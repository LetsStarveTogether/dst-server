# 批量交易 MOD 兼容性审查

审查日期：2026-09-07。
[Stacked Trade／批量交易（3046339764）][workshop] 1.2.1 存在默认配置即可触发的蚁狮无限循环。
该问题不依赖其他 MOD。
用户随后接受本报告中的已知问题，要求保留默认配置并更新现有半纯净房间。
070 房地面和洞穴均确认保存至快照 159 后停止游戏，更新配置、下载 MOD 并恢复运行。
两个分片实际加载版本均为 1.2.1，六项运行时配置与默认值完全一致，存档会话保持原样，跨分片连接已就绪。
050 房同步更新配置，保持原有停机状态；原四个 MOD 的配置均保留。

半纯生存 050–069、半纯无尽 070–099 的地面和洞穴使用同一份配置。
新 MOD 已加入共享下载清单的生成来源，并沿用其他 MOD 的显式配置方式。
以下六项逐一核对过下载包的 `modinfo.lua`，保留 1.2.1 的上游默认值。

云霄国度、岛屿冒险及其他房型没有新增此 MOD。
模板和已部署的 070 房均保留上游默认值，包含 `antlion = true`；下述缺陷没有在本次部署中修补。

本次在一次性 Podman 容器内用 SteamCMD 匿名下载工坊原包，未修改其 Lua。
包内只有 `modinfo.lua`、`modmain.lua` 两个 Lua 文件，均可解析。
`modmain.lua` 的 SHA-256 为 `bff4ac71c452fcd5a9a4f0ed45c5a035c66e7a55b63757dd04df386bae691fca`。
`modinfo.lua` 的 SHA-256 为 `f42c9bf804baa4a3668d2c739e1818ccba53947d684168ee9284a963c03bdde2`。
下文 MOD 行号以这一下载包为准。

SteamCMD 在线查询确认专服 `343050` 当前正式分支 Build ID 为 `24700372`，对应游戏版本 `747465`。
本机镜像的版本和 Build ID 相符，镜像内游戏 Lua 与仓库对应的交易代码逐字节相同。
另外核对了公开测试版 `751622` 的[游戏 Lua 快照][beta]。
该测试版的六个交易目标、`trader` 和猴女王状态图与正式版相同；`actions.lua` 和 `eater.lua` 的改动不涉及本次交易路径。

| 严重性 | 已确认的问题 | 触发条件与影响 |
| --- | --- | --- |
| 严重 | 蚁狮奖励列表自我追加，无限循环 | 一次交付至少两个沙滩玩具 `antliontrinket` 或红眼冠 `cotl_trinket`；主模拟线程无法返回，奖励表持续增长，有内存耗尽风险。 |
| 中 | 猪王遗漏当前原版万圣节奖励 | MOD 复制的发奖函数缺少原版的幸运判定与南瓜雕刻工具掉落分支；包括单件交易。 |
| 低 | 部分失败交易显示动作成功 | 猪王、蚁狮、猴女王等路径忽略 `AcceptGift` 的失败返回；接收条件仍执行，已验证被禁用的交易者不会消费物品。 |
| 潜在 | 跳过原版交付前置逻辑 | 白名单目标直接调用 `AcceptGift`，绕过旧 `GIVE` 的口袋物品限制和容量预检；合成物品可复现，但未确认现有组合中具体受影响的正常物品。 |

蚁狮的根因位于 MOD `modmain.lua:110–115`。
当原版奖励为表时，`rewardlist` 和 `pending` 指向同一张表，`ipairs(rewardlist)` 每次循环又向 `pending` 追加元素，遍历永远到不了结尾。
原版 [antlion.lua:135–137][antlion] 正好给沙滩玩具与红眼冠返回奖励表，而且两种物品本来就能堆叠。
这不是需要额外堆叠 MOD 才能触发的假设。

复现检查加载未修改的 MOD、原版 `Trader` 和原版 `OnGivenItem`，并用 Lua 指令钩子主动截断循环。
两个物品各两份的用例均超过十万条指令，奖励表分别增长到 8299、8300 项；正式版和测试版结果一致。
同一检查中，原版从两份物品中单份交易、MOD 单件交易，以及普通石头／普通玩具的四十份交易均正常返回。
根本修复应让奖励模板独立于追加目标，并按原始奖励数量追加；本次未向第三方 MOD 注入修补代码。

猪王问题可直接对照 MOD `modmain.lua:23–93` 与原版 [pigking.lua:111–115][pigking]。
使用双方真实奖励函数、固定万圣节与幸运判定通过的检查中，原版两次交易得到两把工具，而 MOD 整组两份得到零把。
鸟笼使用的是另一种实现：MOD 在 `modmain.lua:426–439` 逐份调用原版 `AcceptGift(..., 1)`。
这条路径保留当前原版的幸运值、消化产物和亮喙鸟喂食冷却判定，不能把早期版本的鸟笼评论直接当作 1.2.1 的缺陷。

鱼人王只支持批量喂食非鱼食物，不包括批量交鱼换奖励；饥饿接近上限时仍会吃掉整组，超出上限的营养会浪费。
默认关闭的猴岛传送门使用内存中的任务队列，未接入保存；若以后开启，需要单独验证重启是否丢失已经交付但尚未兑换的剩余份数。

| 大型 MOD 与交叉点 | 审查结论 |
| --- | --- |
| 云霄国度的鸟笼 | 云霄自己的 `trader.onaccept` 保留；逐份交易继续调用猪镇消化逻辑，Lua 检查验证四份肉产生四个蛋。 |
| 云霄国度的居民、商店、猪女王 | `pigman_*` 等不在六个原版目标白名单中，沿用原流程，没有新增批量功能。 |
| 岛屿冒险的鸟笼、海盗鹦鹉 | 海难主要改 `occupiable` 和 `shelf`，没有覆盖交易回调，未发现直接冲突。 |
| 岛屿冒险的鱼人王 | 核心优先级高于批量交易；后者包装核心回调，非鱼食物批量进食，鱼和特殊装备仍回到核心回调。 |
| 岛屿冒险的八爪鱼王、火山祭坛 | 不在白名单中，仍经过海难原来的 `GIVE`；不提供批量交易，也没有直接取消每日交易限制。 |
| 岛屿冒险的蚁狮 | 核心只包装战斗与中毒逻辑，不改奖励队列；无法修复批量交易自身的无限循环。 |

上述结论来自本机云霄国度 `1.0.48`、岛屿冒险海难 `1.0.58`、核心 `1.0.70` 的完整源码。
关键交叉文件同时与作者当前源码核对，规范换行后相同：[云霄鸟笼][hamlet]、[核心鱼人王][ia-core]、[海难动作][ia]。
核心工坊页面已显示 `1.0.71`；作者仓库 HEAD 不等于该工坊版本的精确发布包。
没有证据表明此 MOD 取消船只、跨平台或室内距离检查，因为动作属性和 `BufferedAction` 的有效性检查仍保留。
`shipwrecked_compatible = false` 是单机 DLC 元数据，不能直接解释为不兼容联机版岛屿冒险。

半纯净已有四个 MOD 的本机源码也作了针对性检查。
自动堆叠处理生成后的物品，Insight 读取蚁狮状态，清理和整理 MOD 未覆盖这六类交易回调，未发现直接覆盖冲突。
大量交易仍会集中生成掉落物并触发自动堆叠／拾取扫描；本次没有做多人压力测试，因此不作性能保证。

房间模板测试为 39 项通过、24 项跳过；跳过原因是仓库不包含历史房间样本。
测试覆盖新默认值、地面和洞穴的一致性、下载清单、配置落盘后重读，以及其他房型的 MOD 集合。
相关 Python 文件通过 Ruff 检查和格式检查。
另外用无网络、限额 2 GiB 内存和 2 CPU 的临时 Podman 容器启动了原版 `747465`，创建独立离线世界并加载原始工坊 Lua。
测试通过控制台创建人物与物品，直接调用服务端 `ACTIONS.GIVE.fn`；这不覆盖真实客户端输入或联机网络路径。

七项普通交易结果均通过结果断言，测试容器已删除。
蚁狮特殊贡品的无限循环已用前述受限 Lua 检查复现，未取得有效的真实游戏复现结果。
大型 MOD 的验证包括真实 Lua 回调与小型引擎替身，未启动云霄国度或岛屿冒险世界。
即使普通交易冒烟测试通过，也不足以消除已复现的默认蚁狮问题。

修复或更新上游 MOD 后，应重新验证两种特殊蚁狮贡品、普通贡品、猪王节日奖励、失败交易、玩家离线和存档重载。
本轮按用户确认保留上游实现与默认配置；两个大型 MOD 继续保持未启用状态。
